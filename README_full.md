# bsl-ls-mcp — MCP-обёртка над BSL Language Server

**bsl-ls-mcp** — Python-обёртка над [BSL Language Server](https://github.com/1c-syntax/bsl-language-server)
(`1c-syntax/bsl-language-server`), которая отдаёт наружу MCP-инструменты для
статического анализа и навигации по коду 1С (BSL). Сервер (jar) и обёртка работают
вместе, нативно на Windows, без Docker. Наружу — один набор инструментов
`mcp__bsl-ls__*`, подключаемый к любому MCP-клиенту. Короткая версия README —
в [README.md](README.md).

**Требования:** Windows; Python 3.10+ или готовый бандл; Java 17+ или portable JRE
в бандле; рабочая копия исходников 1С в формате CR-выгрузки.

## Структура
```
server/   bsl-language-server-0.29.0-exec.jar   — сервер (pin v0.29.0)
pyproject.toml                                  — пакет (pip install -e .), команда bsl-ls-mcp
build.ps1 + run.cmd                             — сборка нативного бандла + запуск (см. ниже)
build-tray.ps1                                  — сборка трей-пультика bsl-ls-tray.exe
install-service.ps1 (+ nssm.exe в бандле)       — установка Windows-службы
src/bsl_ls_mcp/                                 — обёртка (clean-lite)
  settings.py            пути/память/status-файл из ENV
  cli.py                 main(): выбор транспорта (stdio/sse/streamable-http), --selftest/--reindex
  bootstrap.py           composition root: build_lsp()/build_analyzer() — знает про infrastructure
  domain/
    models.py            формы ответа (SymbolRef, CodeLocation, Diagnostic, Complexity)
    ports.py             порты LspServer (навигация) и CodeAnalyzer (проверка кода)
    resolver.py          имя 1С → (файл, позиция) для навигации; → srcDir для analyze
    mapper.py            LSP/analyze-ответ → имена 1С
    one_c_naming.py      таксономия типов EN↔RU  (pure, без IO)
    one_c_config_path.py карта каталог↔тип, разбор пути  (pure, без IO)
  infrastructure/
    stdio_lsp_client     навигация: тёплый java lsp + JSON-RPC по stdio + status-файл
    analyze_cli          проверка кода: разовый java analyze (без индекса) + очередь
  application/     tools (7 инструментов), server (FastMCP, семафор конкурентности)
tray/tray.py                                     — исходник трей-пультика (лампочка статуса)
scripts/run_mcp.py                               — entry-point (PyInstaller / запуск без установки)
scripts/mcp_query.py                             — ручной MCP-запрос к живому демону
tests/fixtures/smoke_ws/                         — мини-конфигурация для тестов
```

## Архитектура: два пути (навигация ↔ проверка кода)

Инструменты делятся по тому, нужен ли им **полный кросс-корпусный индекс**:

```
bsl-ls-mcp.exe (служба :8081)
├─ LspServer    тёплый java (stdio, ~12 ГБ, держит граф)   → callers/callees/definition/references/complexity
└─ CodeAnalyzer разовый java analyze (~2 ГБ, очередь)      → diagnostics
```

- **Навигация** (`callers`, `callees`, `definition`, `references`) реально требует индекса: найти
  все вызовы/ссылки по базе можно только проиндексировав всё. Поэтому держим ОДНУ тёплую
  LSP-сессию — иначе индекс пришлось бы строить заново на каждый вызов. На тёплом индексе
  ответ — доли секунды.
- **Проверка кода** (`diagnostics`) — пофайловый статический анализ, индекс ему НЕ нужен.
  Идёт через пакетный `bsl-language-server analyze` (разовый java, ~5–8 c, без графа и без
  ожидания индекса). Один и тот же jar, но память графа не делится.
- Почему так: гонять диагностики через тёплый LSP — это ждать полный индекс и упираться в
  таймаут на крупных модулях/формах (форма 1 МБ давала 0 за 120 c). `analyze` ту же форму
  считает за 8 c. Это же подтверждают сторонние MCP-обёртки над bsl-ls (phsin — `analyze`-CLI
  для диагностик; FSerg — раздельные инструменты check/nav).

## Запуск с нуля (пошагово)

Нужно в любом случае: рабочая копия исходников 1С (CR-выгрузка) и **~14 ГБ
свободной RAM** (live-set индекса корпуса ~12.6 ГБ; меньше — вечный GC).

### Сценарий А — машина с Python 3.10+ и Java 17+ (разработка)
```powershell
cd ...\bsl-ls-mcp
py -3 -m pip install -e .                      # 1. установка пакета
$env:BSL_WORKSPACE = "C:\1c\src\cf"             # 2. путь к исходникам 1С
bsl-ls-mcp --selftest                           # 3. проверка: индекс + диагностики → [selftest] OK
bsl-ls-mcp --transport streamable-http --port 8081   # 4. демон → http://127.0.0.1:8081/mcp
```

### Сценарий Б — чистая машина БЕЗ Python и Java
Бандл самодостаточен (внутри Python и JRE). Собирается один раз на машине-сборщике.

**Сборка (на машине с Python):**
```powershell
powershell -ExecutionPolicy Bypass -File build.ps1          # → dist\bsl-ls-mcp\ (exe + server\jar + run.cmd)
# положить portable Temurin JRE 21 в dist\bsl-ls-mcp\jre\ (чтобы был jre\bin\java.exe):
#   https://adoptium.net/temurin/releases/?version=21  (Windows x64 JRE .zip)
```

**На целевой машине:**
```bat
:: 1. Скопировать всю папку dist\bsl-ls-mcp\ на машину.
:: 2. Указать путь к исходникам 1С — отредактировать BSL_WORKSPACE в run.cmd
::    (или задать заранее:  set BSL_WORKSPACE=E:\1c\src\cf )
:: 3. Проверка — должно напечатать [selftest] OK (первый раз индексирует ~1.5 мин):
run.cmd --selftest
:: 4. Запуск демона:
run.cmd
::    → "Uvicorn running on http://127.0.0.1:8081" (окно не закрывать; Ctrl+C — остановка)
```
`run.cmd` сам подхватит `jre\bin\java.exe`, если он есть (иначе системную java).
Python на целевой машине НЕ нужен — он внутри exe.

### Как Windows-служба (автозапуск, переживает logoff/перезагрузку)
Демон лучше держать службой (авто-старт при загрузке, авто-рестарт при падении,
без консоли). Обёртка для этого — **NSSM** (в бандле уже лежит `nssm.exe`).
**Из-под администратора:**
```powershell
powershell -ExecutionPolicy Bypass -File install-service.ps1 -Workspace "E:\1c\src\cf"
```
Скрипт ставит службу `bsl-ls-mcp` (streamable-http :8081), задаёт ENV, авто-рестарт,
автозапуск, и стартует её. java гасится вместе со службой через **Job Object**
(`kill-on-close`) — сирот не остаётся даже при `taskkill /F`.
```
sc query bsl-ls-mcp            :: статус
nssm restart bsl-ls-mcp        :: рестарт
nssm stop bsl-ls-mcp ; nssm remove bsl-ls-mcp confirm   :: удалить
```

### Трей-пультик (опционально, на рабочей станции)
`bsl-ls-tray.exe` (в бандле) — иконка в области уведомлений с цветной надписью «BSL»,
отражающей состояние (служба + индекс): 🟢 **готов** · 🟡 **индексирую…** · 🟠 поднята
(индекса ещё нет) · 🔴 остановлена · ⚪ не установлена. Состояние индекса трей читает из
status-файла (`BSL_STATUS_FILE`, по умолчанию `%ProgramData%\bsl-ls-mcp\status.json`),
который пишет демон; служба определяется через `sc query`. Меню: Запустить · Остановить ·
**Переиндексировать** · Открыть логи · Установить службу. Сам демоном не является —
командует NSSM-службой (управляющие действия — через UAC). Запуск: `bsl-ls-tray.exe`
(удобно добавить в автозагрузку пользователя). Сборка: `build-tray.ps1`.

«Переиндексировать» в трее = рестарт службы (полный свежий индекс). Есть и in-place
реиндекс без обрыва соединений — MCP-инструмент `bsl_reindex` (см. методы).

### Подключение к MCP-клиенту
Демон поднят (Сценарий А шаг 4 или Б шаг 4; либо как служба). В `.mcp.json` вашего
MCP-клиента (Claude Code и совместимые) добавьте сервер — по выбранному транспорту:
```json
{ "bsl-ls": { "type": "streamable-http", "url": "http://127.0.0.1:8081/mcp" } }
{ "bsl-ls": { "type": "sse",             "url": "http://127.0.0.1:8081/sse" } }
```
Первый вызов подождёт индекс (~1.5 мин), дальше — мгновенно (тёплый демон).

**Какой транспорт:** `sse` **устарел** (deprecated в спеке MCP 2025-03-26),
актуальная замена — `streamable-http`. `sse` даёт совместимость с MCP-клиентами
на `type: sse`; `streamable-http` — future-proof, требует поддержки на стороне
MCP-клиента. `stdio` не устарел, но для большой конфигурации непрактичен (переиндексация
на каждую сессию). Все три доступны одним флагом `--transport`.

## Переменные окружения
Все параметры обёртки централизованы в `settings.py` (`Settings.from_env`) и
управляются через ENV. Группы: источник/пути · JVM · MCP-транспорт · тайминги.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| **источник/пути** | | |
| `BSL_WORKSPACE` | `C:\1c\src\cf` | исходники базы 1С (рабочая копия, её индексирует сервер). **Смена подхватывается только полным рестартом службы** — см. ниже |
| `BSL_LS_JAR` | `server/bsl-language-server-0.29.0-exec.jar` | путь к jar сервера |
| `BSL_CONFIG` | — | путь к `.bsl-language-server.json` (необязательно) |
| `BSL_SERVER_LOG` | — | файл для stderr java-сервера (диагностика); пусто — отбрасывать |
| `BSL_STATUS_FILE` | `%ProgramData%\bsl-ls-mcp\status.json` | файл состояния индекса (`idle`/`building`/`ready`) — пишет демон, читает трей |
| **JVM** | | |
| `BSL_JAVA` | `java` | путь к java (для portable JRE в бандле); по умолчанию из PATH |
| `BSL_XMX` | `14g` | память JVM. live-set индекса корпуса ~12.6 ГБ; **Xmx < live-set → вечный GC и зависание** — давать с запасом |
| **MCP-транспорт (адрес/порт)** | | |
| `BSL_MCP_TRANSPORT` | `stdio` | транспорт: `stdio` \| `sse` (устар.) \| `streamable-http` |
| `BSL_MCP_HOST` | `127.0.0.1` | host для SSE-демона |
| `BSL_MCP_PORT` | `8081` | port для SSE-демона |
| `BSL_MAX_CONCURRENCY` | `4` | макс. одновременных операций навигации к единственной LSP-сессии (очередь) |
| `BSL_DIAG_MAX_CHARS` | `30000` | бюджет размера списка диагностик (символы); сверх — `warning` сворачиваются в сводку (`error` всегда целиком) |
| **проверка кода (analyze-CLI)** | | |
| `BSL_ANALYZE_XMX` | `2g` | heap разового java `analyze` (пофайловый анализ, не граф) |
| `BSL_ANALYZE_CONCURRENCY` | `1` | очередь: сколько `analyze`-процессов разом (1 = строго последовательно) |
| `BSL_ANALYZE_TIMEOUT` | `300` | таймаут одного `analyze`-прогона (сек) |
| **тайминги (сек)** | | |
| `BSL_REQUEST_TIMEOUT` | `1200` | таймаут одиночного LSP-запроса |
| `BSL_INDEX_WAIT_TIMEOUT` | `1200` | макс. ожидание готовности индекса (предохранитель) |
| `BSL_INDEX_SETTLE` | `3` | затихание `$/progress` → индекс готов |
| `BSL_INDEX_GRACE` | `20` | ожидание начала `$/progress` (fallback, если сервер молчит) |
| `BSL_DIAGNOSTICS_WAIT` | `120` | ожидание `publishDiagnostics` по файлу |

CLI-флаги `run_mcp.py` (`--transport/--host/--port`) переопределяют ENV при запуске.

### ⚠️ Смена базы (`BSL_WORKSPACE`) требует РЕСТАРТА СЛУЖБЫ, не реиндекса
`get_settings()` кэшируется при старте **процесса**, а `bsl_reindex` перезапускает только
java **внутри того же процесса** и ENV заново не читает. Поэтому «поменял путь в nssm →
нажал Переиндексировать» **не работает** — демон продолжит индексировать старое дерево.

```powershell
nssm edit bsl-ls-mcp        # вкладка Environment -> поправить BSL_WORKSPACE (не затирая остальные)
nssm restart bsl-ls-mcp     # ОБЯЗАТЕЛЬНО: полный рестарт процесса, иначе путь не подхватится
```
Проверить, что реально стоит у службы: `nssm get bsl-ls-mcp AppEnvironmentExtra`.
Быстрый оракул «то ли дерево индексируется»: поправить файл на диске → `bsl_diagnostics`
(analyze читает диск напрямую) должен изменить число диагностик; не изменил — демон
смотрит не туда.

### Свежесть: что живое, а что снимок
| Уровень | Свежесть |
|---|---|
| Диагностики (`analyze`) | **живые** — читают диск на каждый вызов |
| `definition`/символы запрошенного модуля | **живые** — через `didChange` |
| Граф `callers`/`callees`/`references` | **СНИМОК** — `didChange` его не перестраивает, нужен `bsl_reindex` |

То есть добавленный вызов появится в `references` только после реиндекса.

## Нативный бандл (без Docker / Python / Java) — рекомендуемая поставка
Bind-mount исходников 1С в Docker на Windows (WSL2/9p) — главный тормоз. Нативный запуск
читает с NTFS на полной скорости. Бандл = одна папка без установки Python:
```
bsl-ls-mcp\
├─ bsl-ls-mcp.exe     ← PyInstaller: Python + mcp + uvicorn (~160 МБ)
├─ server\bsl-language-server-0.29.0-exec.jar
├─ run.cmd            ← задаёт ENV (BSL_LS_JAR/BSL_JAVA/BSL_WORKSPACE/BSL_XMX=14g) и стартует демон
└─ jre\               ← ОПЦИОНАЛЬНО: portable Temurin JRE 21, только если на машине нет Java
```
**Java:** по умолчанию `run.cmd` берёт системную `java` (нужна **17+**, работает на 21) —
`BSL_JAVA` это и задаёт. Бандлить JRE нужно **только** для машины без Java: положить
portable Temurin JRE 21 в `jre\` и раскомментировать `BSL_JAVA=...\jre\bin\java.exe`.
(Реальную боль снимает не отказ от Java, а отказ от Docker — bind-mount исходников в WSL2.)

Сборка: `powershell -ExecutionPolicy Bypass -File build.ps1` → `dist\bsl-ls-mcp\`.
Запуск демона: `run.cmd` (streamable-http на :8081/mcp). «Один exe» невозможен из-за JVM
(нужно ~14 ГБ кучи): exe поднимается, стартует java, сервит MCP (`/mcp` отвечает).

## Методы (инструменты MCP) и параметры

Обёртка даёт 7 инструментов (префикс `mcp__bsl-ls__*`): 6 рабочих (ниже) плюс
обслуживающий `bsl_reindex`. Все рабочие принимают на
вход **имя объекта 1С строкой** и возвращают **JSON-список** в русских именах
(форма ответа — русские имена 1С, как в `ПолноеИмя()`). Ниже — что каждый делает, что принимает и что отдаёт,
с примерами.

### Как устроено имя (читать первым)

Везде, где инструмент просит имя, это строка с точками. Два формата:

```
Тип . Модуль . Символ        ← навигация по функции/процедуре
Тип . Модуль                 ← операции над целым модулем (диагностики, сложность)
```

| Часть | Что это | Примеры |
|---|---|---|
| **Тип** | вид объекта 1С по-русски (как в `ПолноеИмя()`) | `ОбщийМодуль`, `Справочник`, `Документ`, `РегистрСведений`, `Обработка`, `Отчет` … |
| **Модуль** | имя самого объекта в конфигурации | `РасчётыСервер`, `ДоговорыКонтрагентов` |
| **Символ** | имя процедуры/функции точно как в коде | `ВычислитьСуммуПоДоговору` |

Полный список типов — в `domain/one_c_naming.py` (40 видов). Неизвестный тип →
понятная ошибка. Пример полного имени функции:

```
ОбщийМодуль.РасчётыСервер.ВычислитьСуммуПоДоговору
└── тип ──┘ └── модуль ──┘ └────── символ ───────┘
```

Как обёртка находит код по имени: `Тип`→каталог выгрузки (`ОбщийМодуль`→`CommonModules`),
`Модуль`→подкаталог (детерминированно, по карте каталогов выгрузки). Точную **позицию
символа даёт сам сервер** (`textDocument/documentSymbol`) — не текстовый поиск по
`.bsl`, поэтому устойчиво к форматированию/комментариям. Для прикладных объектов
перебираются модули менеджера/объекта/набора, берётся тот, в чьём символ-дереве есть метод.

### Поля ответов (общие структуры)

Навигация по вызовам (`callers`/`callees`) → список **`SymbolRef`**:

| поле | смысл |
|---|---|
| `name` | имя символа |
| `type` | тип объекта 1С (рус.) |
| `full_name` | полное имя `Тип.Модуль.Символ` — можно сразу подать в другой инструмент |
| `kind` | `procedure` \| `function` \| `class` \| `constructor` \| `unknown` |

Места в коде (`definition`/`references`) → список **`CodeLocation`**:

| поле | смысл |
|---|---|
| `type`, `module`, `full_name` | где находится (объект, в котором встретился символ) |
| `line` | номер строки, **1-based** (как в редакторе) |
| `text` | сама строка кода — видно контекст, не открывая файл |

Диагностики → объект `{diagnostics, suppressed}`, где `diagnostics` — список
**`Diagnostic`**: `file`, `line` (1-based), `code` (ключ правила BSL LS), `severity`
(`error`/`warning`/`info`/`hint`), `message` (подробности — в разделе метода 1).

Сложность → список **`Complexity`**: `full_name`, `cognitive`, `cyclomatic` (числа).

---

### 1. `bsl_diagnostics(module_full_name=None, path=None, text=None, min_severity="warning", code=None)`
**Что делает:** проверяет код и возвращает замечания BSL LS (ошибки, стиль,
устаревшие конструкции). Это **блокирующий шаг** — нельзя сдавать код с ошибками.

**Идёт через пакетный `analyze` (не тёплый LSP):** разовый java (~5–8 c), **без индекса**
и без ожидания готовности графа — поэтому работает и на гигантских модулях/формах, где
LSP-путь упирался в таймаут (см. «Архитектура: два пути»). Поддерживает **модули форм**:
`Тип.Объект.Форма.ИмяФормы` (каноничное 4-частное) и `…Форма.ИмяФормы.Форма` (5-частное) —
резолвятся в папку формы `Forms/ИмяФормы/Ext/Form`, а не в `ManagerModule`.

**Три способа адресации (ровно один за вызов):**
- `module_full_name` — модуль **проиндексированного корпуса** (резолв по дереву `BSL_WORKSPACE`);
- `path` — **произвольный каталог или `.bsl`-файл ВНЕ корпуса**: внешние обработки/отчёты
  (`work/<ИД>/Реализация/...`), любой чужой каталог. Индекс не нужен — `analyze` берёт папку
  как есть. Если передан файл — анализируется его каталог, а отчёт фильтруется по этому файлу.
  Подпись `file` для такого кода — путь относительно переданного `path`
  (напр. `Ext/ObjectModule.bsl`, `Forms/Форма/Ext/Form/Module.bsl`).
- `text` — **строка кода 1С (снипет)**: линт до записи в файл (сгенерированный/предлагаемый
  код). Пишется во временный `.bsl` → `analyze` → temp удаляется. **Обёртка в процедуру НЕ
  нужна** — блок операторов линтуется как есть (инициализация структуры со строкой
  146 символов → `LineLength` пойман); нужна лишь синтаксическая **завершённость** — закрытые
  `Если`/`Цикл`, не оборванные выражения (иначе `ParseError`). Проверки **пофайловые, без
  контекста конфигурации** — тип модуля, ссылки на объекты НЕ проверяются, только
  синтаксис/стиль/качество. Подпись `file` = `<snippet>`. Для полной проверки — записать в
  модуль и звать по имени/`path`. **Для снипета по умолчанию возвращаются ВСЕ замечания**
  (не только `error`+`warning`) — объём мал, а стиль (длина строк, пробелы) как раз интересен;
  явный `min_severity` переопределяет.

На крупных модулях (формы) диагностик сотни, и стилевой шум (`hint`/`info`)
переполняет бюджет клиента. Поэтому по умолчанию инструмент отдаёт **полным списком
только `error`+`warning`**, а `info`/`hint` **сворачивает в сводку-счётчики** — ничего
не теряя: клиент видит, чего и сколько отсеяно, и дозапрашивает детали.

| параметр | тип | формат | пример |
|---|---|---|---|
| `module_full_name` | str (опц.*) | `Тип.Модуль` или `Тип.Объект.Форма.Имя` | `"Справочник.Контрагенты.Форма.ФормаЭлемента"` |
| `path` | str (опц.*) | каталог или `.bsl`-файл вне корпуса | `r"C:\1c\work\<задача>\Реализация"` |
| `min_severity` | str (опц.) | `error`\|`warning`\|`info`\|`hint` | деф. `"warning"` — порог для полного списка |
| `code` | str (опц.) | ключ правила | `"Typo"` — drill-down: все по коду, любой severity |

\* `module_full_name` и `path` — **взаимоисключающие**: ровно один за вызов. Ни одного,
оба сразу или несуществующий путь → понятная ошибка резолва.

**Возвращает объект** `{diagnostics, suppressed}`:
```json
{ "diagnostics": [
    {"file":"...Форма","line":2,"code":"CommonModuleInvalidType",
     "severity":"error","message":"Общий модуль недопустимого типа"} ],
  "suppressed": { "total": 186,
    "by_code": [ {"code":"SpaceAtStartComment","severity":"hint","count":54},
                 {"code":"LineLength","severity":"info","count":46},
                 {"code":"Typo","severity":"hint","count":21} ] } }
```
- `diagnostics` — показанные (по убыванию severity, error первыми); пустой = чисто по порогу.
- `file` — **точная подпись модуля** по пути файла из отчёта (детерминированно, не парс имени):
  у объекта с несколькими модулями в `Ext` замечания различаются —
  `Справочник.X.МодульМенеджера` vs `…МодульОбъекта`; у формы — `Справочник.X.Форма.Имя`.
- `suppressed.by_code` — что свёрнуто (счётчики по кодам). Чтобы раскрыть конкретное —
  вызвать с `code="Typo"` (вернёт все 21, независимо от severity).
- **Страховка по объёму:** если даже `error`+`warning` не влезает в бюджет
  (`BSL_DIAG_MAX_CHARS`, деф. 30000 символов), `warning` тоже сворачиваются в сводку
  (`error` остаются всегда), и в `suppressed.note` появляется пометка. Если и одни
  `error` за бюджетом — отдаются как есть (ошибки важнее лимита).

**Когда:** гейт качества перед сдачей кода; обязательный прогон на ревью.

### 2. `bsl_callers(full_name)`
**Что делает:** находит, **кто вызывает** эту функцию — по всему корпусу, между
модулями. Главный инструмент анализа влияния: «кого заденет моя правка X».

| параметр | тип | формат | пример |
|---|---|---|---|
| `full_name` | str | `Тип.Модуль.Символ` | `"ОбщийМодуль.РасчётыСервер.ВычислитьСуммуПоДоговору"` |

**Возвращает** `list[SymbolRef]` — вызывающие. Пример ответа:
```json
[ {"name":"ЗаполнитьДанныеНаСервере","type":"Справочник",
   "full_name":"Справочник.Контрагенты.ЗаполнитьДанныеНаСервере","kind":"procedure"},
  {"name":"ОбновитьСуммуНаСервере","type":"Справочник",
   "full_name":"Справочник.Контрагенты.ОбновитьСуммуНаСервере","kind":"procedure"} ]
```
То есть функция общего модуля вызывается из двух методов модуля справочника —
правка функции затронет оформление договоров. **Когда:** анализ влияния перед правкой.

### 3. `bsl_callees(full_name)`
**Что делает:** обратное к `callers` — **кого вызывает** эта функция (исходящие вызовы).
Помогает понять, от чего зависит метод.

| параметр | тип | формат | пример |
|---|---|---|---|
| `full_name` | str | `Тип.Модуль.Символ` | `"ОбщийМодуль.МойМодуль.ВычислитьСумму"` |

**Возвращает** `list[SymbolRef]` — вызываемые функции (пустой = ничего пользовательского не зовёт).

### 4. `bsl_definition(full_name)`
**Что делает:** показывает, **где объявлен** символ (переход к определению).

| параметр | тип | формат | пример |
|---|---|---|---|
| `full_name` | str | `Тип.Модуль.Символ` | `"ОбщийМодуль.МойМодуль.ВычислитьСумму"` |

**Возвращает** `list[CodeLocation]` (обычно один — место объявления). Пример:
```json
[ {"type":"ОбщийМодуль","module":"РасчётыСервер",
   "full_name":"ОбщийМодуль.РасчётыСервер","line":16,
   "text":"Функция ВычислитьСуммуПоДоговору(Договор) Экспорт"} ]
```

### 5. `bsl_references(full_name)`
**Что делает:** находит **все места использования** символа (без самого объявления).
В отличие от `callers` (только вызовы функций), сюда попадают любые упоминания.

| параметр | тип | формат | пример |
|---|---|---|---|
| `full_name` | str | `Тип.Модуль.Символ` | `"ОбщийМодуль.МойМодуль.ВычислитьСумму"` |

**Возвращает** `list[CodeLocation]` — каждое использование со строкой кода. Пример:
```json
[ {"type":"Справочник","module":"Контрагенты","full_name":"Справочник.Контрагенты",
   "line":142,"text":"Сумма = РасчётыСервер.ВычислитьСуммуПоДоговору(Договор);"} ]
```

### 6. `bsl_complexity(module_full_name, function=None)`
**Что делает:** считает **сложность методов** модуля — две метрики: цикломатическую
(число путей выполнения ≈ сколько тестов нужно) и когнитивную (насколько тяжело
читать человеку). Готовая метрика ревью «эти методы стоит упростить».

| параметр | тип | формат | пример |
|---|---|---|---|
| `module_full_name` | str | `Тип.Модуль` | `"ОбщийМодуль.МойМодуль"` |
| `function` | str (опц.) | имя метода | `"БольшаяФункция"` — только она; иначе все методы |

**Возвращает** `list[Complexity]` по методам:
```json
[ {"full_name":"ОбщийМодуль.МойМодуль.ВычислитьСумму","cognitive":1,"cyclomatic":2},
  {"full_name":"ОбщийМодуль.МойМодуль.ЗаписатьРезультат","cognitive":0,"cyclomatic":1} ]
```
**Когда:** флаг «слишком сложно» на ревью; оценка риска правки.

### 7. `bsl_reindex()`
**Полный реиндекс** корпуса in-place (после массовых изменений конфигурации —
много файлов, перенос подсистемы). Точечные правки модулей подхватываются **сами**
(через `didChange`), для них реиндекс не нужен. Гасит и поднимает java заново, **не
роняя демон и соединения**; следующий вызов подождёт новый индекс (~1.5 мин).
- Параметров нет. Возвращает `{"status":"reindexing", ...}`.

### Поведение и ошибки
- **Первый вызов НАВИГАЦИИ после старта ждёт индексацию** (на большой конфигурации ~1.5 мин),
  все последующие — мгновенно (доли секунды; см. «Старт и готовность индекса»).
  `bsl_diagnostics` индекса НЕ ждёт (идёт через `analyze`, ~5–8 c всегда).
- **Имя не разрешилось** (нет такого модуля/файла/формы, неизвестный тип) → ошибка резолва
  с пояснением.
- **Символ не найден / нет результатов** → пустой список (не ошибка).

### Какой инструмент для чего
| Инструмент | Задача |
|---|---|
| `bsl_diagnostics` | гейт качества перед сдачей кода и на ревью |
| `bsl_callers` / `bsl_references` | анализ влияния — кого заденет правка |
| `bsl_callees` / `bsl_definition` | понять зависимости и место объявления метода |
| `bsl_complexity` | метрика ревью — какие методы стоит упростить |

## Старт и готовность индекса
LSP-сессия поднимается **лениво при первом вызове инструмента** (а НЕ в FastMCP
`lifespan`: для сетевых транспортов FastMCP запускает lifespan на каждую MCP-сессию,
что гасило бы java на каждое подключение). Сессия **одна на весь демон** и остаётся
тёплой между подключениями клиентов (2-й вызов новой MCP-сессии — ~1 c).
Индексация у BSL LS асинхронная, поэтому первый вызов **не блокируется** на спавне:
- клиент заявляет `window.workDoneProgress` → сервер шлёт `$/progress` индексации;
- BSL LS индексирует тремя фазами; тяжёлая (наполнение контекста) шлёт report-тики
  по файлам. Готовность = **конец тикающей фазы + закрытие всех фаз** (а не просто
  «тишина» — пауза между фазами на большой конфигурации срабатывала преждевременно);
- методы порта ждут готовность (`wait_ready`) → первый вызов подождёт индекс,
  дальше мгновенно. MCP-инициализация клиента при этом не блокируется.

## Конкурентность и свежесть
- **Две очереди (по числу путей):**
  - *навигация* идёт к одной живой LSP-сессии → семафор `BSL_MAX_CONCURRENCY` (деф. 4)
    бережёт сервер от перегруза и RAM-всплесков; лишние вызовы ждут слот;
  - *проверка кода* (`analyze`) — отдельная очередь `BSL_ANALYZE_CONCURRENCY` (деф. 1),
    чтобы разовые java (~2 ГБ) не складывались поверх тёплого графа (~12 ГБ).
- **Свежесть:**
  - *навигация*: перед запросом обёртка синхронизирует файл модуля с диском
    (`didChange` по mtime) — правки модулей видны **без перезапуска и переиндекса**
    (дописали процедуру на диск → появилась в ответе); лишних `didChange` нет.
    Ограничение: подхватывается изменённый/запрашиваемый модуль; новый вызывающий в
    другом, не запрошенном файле появится только после его запроса или рестарта.
  - *диагностики*: `analyze` каждый раз читает файлы с диска заново — всегда свежо,
    синхронизация не нужна.

## Ограничения
- **Только Windows.** Поставка завязана на Windows: NSSM-служба, `.ps1`-скрипты,
  `run.cmd`, гашение java через Job Object. Кроссплатформенной сборки нет.
- **Граф вызовов/ссылок — снимок.** `callers`/`callees`/`references` отвечают по индексу,
  построенному при старте (или последнем `bsl_reindex`). Новая связь между модулями
  появится в ответе только после `bsl_reindex`; `didChange` обновляет лишь определения и
  символы запрошенного модуля, но не перестраивает граф (см. таблицу «Свежесть»).
- **`bsl_diagnostics` не ловит «переменная/метод не определён».** Это пофайловый
  статический анализ синтаксиса, стиля и качества; семантики областей видимости у
  bsl-language-server нет. Проверку «объект/метод не существует» делает синтакс-контроль
  конфигуратора/EDT.
- **У `bsl_complexity` нет параметра `path`.** Сложность считается только по модулям
  проиндексированного корпуса; код вне `BSL_WORKSPACE` не покрывается.
